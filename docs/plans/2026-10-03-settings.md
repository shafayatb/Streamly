# Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace Profile's "Settings are coming soon" stub with a real, device-wide Settings
screen: theme (System / Light / Dark), Wi-Fi-only downloads, and download quality (360p / 480p /
720p), plus an About row with the app version.

**Architecture:** `:domain` gets the settings model and two contracts: `SettingsRepository`
for screens, and a narrow `DownloadPreferencesSource` for media. `:data` stores the settings in a new
`settings` Preferences DataStore and implements both. `MediaDownloads` in `:core:media` reads
`DownloadPreferencesSource`. It sets the `DownloadManager`'s requirements (`NETWORK` or
`NETWORK_UNMETERED`) and builds each download's track parameters from the chosen quality. A new
`WAITING_FOR_WIFI` download status reaches the Player and Downloads. `AppViewModel` carries the
theme mode in `AppState.Ready`; `App` resolves it into `StreamlyTheme` and a new
`SystemBarsEffect`. A new MVI screen in `:shared` edits the settings.

**Tech Stack:** Kotlin 2.4, Coroutines/Flow, DataStore Preferences, Media3 1.11.1 (`DownloadManager`,
`DownloadHelper`, `Requirements`), Compose Multiplatform 1.12 / Material 3, Navigation 3, Koin 4.2,
`kotlin.test`, `kotlinx-coroutines-test`, Turbine, Compose UI tests.

**Spec:** this file. The design was agreed in chat on October 3 (summary below).

## Agreed design (brainstorming, October 3)

- **Scope (user).** Three settings: **Theme**, **Wi-Fi-only downloads**, **Download quality**.
  Clear watch history stays on the History screen only (not duplicated here). An **About** row
  shows the version.
- **Device-wide (user).** One value per device, kept across sign-out and account switches, and
  editable by a guest. No account key.
- **Quality (user).** Three tiers, default unchanged:
  - Data saver, up to 360p: cap 640x360
  - Standard, up to 480p: cap 854x480, the **default** (today's behaviour)
  - High, up to 720p: cap 1280x720

  Quality applies to **new downloads only**. A finished download keeps its rendition, and so
  does Retry of a failed one, because it re-adds the stored request with its stream keys. A
  stream with no variant under the cap falls back to its lowest variant, as today. No size hint
  is shown, because sizes depend on each stream's bitrates.
- **Wi-Fi only (user).** **Off by default** (today's behaviour). When on:
  - A download on mobile data is accepted and queued, and the app shows **"Waiting for Wi-Fi"**
    instead of "Waiting for network". It starts by itself on Wi-Fi.
  - Turning the switch on pauses running mobile-data downloads the same way. Media3 keeps the
    cached segments, so they resume where they stopped.
  - There's no extra dialog or snackbar.
- **Approach A (user).** Media reads a narrow domain contract.
  - **Contracts:** `DownloadPreferencesSource` is injected into `MediaDownloads`.
    `SettingsRepository` is a separate contract, deliberately *not* a supertype of it, so the
    `DeviceDownloads : DownloadRepository` type-check problem isn't repeated. One `:data` class
    implements both.
  - **Launch is fail-safe.** `DownloadManager` starts paused, and `DownloadService.onCreate`
    resumes it unconditionally (Media3 1.11.1 sources), so pausing until the read wouldn't hold.
    Instead `MediaDownloads.init` sets `Requirements(NETWORK_UNMETERED)` before anything can
    resume. It then applies the stored choice once the DataStore answers. A Wi-Fi-only user never
    spends mobile data, and an any-network user's resumed download starts a few ms later.
  - **No flicker.** The `downloads` flow waits for the first preferences value, so the strict
    start never shows "Waiting for Wi-Fi" to someone who allows mobile data.
  - **Quality per request.** It's read when each download is prepared, so the track parameters
    are built per request.
- **Theme.**
  - **State:** `AppState.Ready(startRoute, themeMode)`. The start route still comes from the
    first session only. The flow then follows the settings, so a theme change emits a new
    `Ready` with the same `startRoute` and the back stack is untouched.
  - **Splash:** it waits for both reads (its condition is still `state == Loading`), so a stored
    Dark never flashes light.
  - **Resolution:** System follows `isSystemInDarkTheme()`, Light is false, and Dark is true.
  - **Window:** a new `SystemBarsEffect(darkTheme, windowBackground)` sets the window background
    to the theme's `background` and the navigation-bar style to match. That fixes the deferred
    "window is white in dark mode" minor in every mode. The status bar keeps light icons over the
    dark brand headers.
  - **Unchanged:** Shorts stays always dark, and onboarding keeps its brand surface.
- **Screen (user: pushed screen + About).**
  - **Navigation:** `Route.Settings` is pushed from Profile's Settings row like Watch history: no
    tab bar, Back returns to Profile, and guests can open it.
  - **Header:** the brand header with Back and "Settings".
  - **Body:** one column, at most 640 dp wide, centred and scrollable:
    - **Appearance:** Theme, with the current value as subtitle.
    - **Downloads:** "Download over Wi-Fi only" as a switch, with "On mobile data, downloads wait
      for Wi-Fi."; then "Download quality", with the current tier; then "Applies to new
      downloads."
    - **About:** "Version" with "1.0 (1)".
  - **Choice dialogs:** Theme and quality open a radio dialog. Picking applies and closes, and
    Cancel closes without a change. The open dialog lives in the ViewModel's state, so it
    survives rotation.
  - **Write failure:** a snackbar says "Couldn’t save the setting. Please try again." The screen
    shows only what the store reports, with no optimistic state.
  - **Loading:** until the settings are read, the rows have no values and are disabled.
- **Version.** `:androidApp` provides `AppInfo(versionName, versionCode)` through Koin from
  `PackageManager`, so `:shared` needs no `BuildConfig`.
- **Fullscreen button (user, out of scope).** It becomes the next feature task,
  `feature/player-fullscreen`, after Settings and before the release gate if time allows on
  October 4; otherwise it's a documented known gap. It goes in `FRESH_PROMPT.md` at the handoff.

### One deviation to confirm with the user before Task 3

The Player's Download button has room for one short word at 360 dp ("Waiting" today; "Waiting
for Wi-Fi" does not fit beside Like and Share). This plan keeps the visible label **"Waiting"** for
both waits. The Wi-Fi wait adds the TalkBack state "Waiting for Wi-Fi", while the Downloads tab and
the notification spell out "Waiting for Wi-Fi". If the user wants the Player to say it visibly,
Task 3 changes only the label string, and the device check at 360 dp decides whether it fits.

## Review Focus

1. **No mobile-data window at launch.**
   - Risk: Wi-Fi only is on, the app is killed mid-download, and it relaunches on mobile data.
     The service resumes the `DownloadManager` before the DataStore answers.
   - Expected: nothing downloads until Wi-Fi.
   - Ordering: `MediaDownloads.init` posts `MSG_SET_NOT_MET_REQUIREMENTS` (strict) after
     `MSG_INITIALIZE` and before the service's `resumeDownloads()`. The internal handler
     processes them in that order.
   - Pinned by: `wifiOnlyRequiresAnUnmeteredNetwork` (Task 4) for the flags, and device step W4
     (kill and relaunch on mobile data). `DownloadManager` cannot run on the host.
2. **No "Waiting for Wi-Fi" flicker for an any-network user.**
   - Risk: the downloads flow must not emit while only the strict start requirement applies.
   - Expected: the first emission already reflects the stored choice.
   - How: in the preferences collector, `setRequirements` runs before the value is published.
   - Pinned by: device step W1 and the review of the collector's order (Task 4, Step 6 comment).
3. **A theme change never resets navigation.**
   - Risk: the theme is changed *on the Settings screen*, so a reset would bounce the user to
     Home.
   - Expected: Settings stays on top, and Back returns to Profile.
   - Pinned by: `aThemeChangeKeepsTheStartRoute` (Task 5) and device step T3.
4. **Quality affects new downloads only.**
   - Risk: a quality change mid-download, or Retry of a failed one, switches rendition.
   - Expected: the existing download keeps its stream keys.
   - How: `retry()` re-adds the stored `DownloadRequest`, unchanged, and only `prepareAndQueue`
     reads the quality.
   - Pinned by: device step Q3, and the code path (Task 4, Step 6).
5. **A failed write never shows as saved.**
   - Risk: the disk is full when a theme is picked.
   - Expected: the dialog closes, a message appears, and the screen still shows the old value.
   - Pinned by: `aFailedSaveShowsAMessageAndKeepsTheStoredValue` (Task 6) and the data test
     `aFullDiskIsReported` (Task 2).

package com.shafayatb.streamly.data.settings

import androidx.datastore.core.DataStore
import androidx.datastore.preferences.core.Preferences
import androidx.datastore.preferences.core.booleanPreferencesKey
import androidx.datastore.preferences.core.stringPreferencesKey
import com.shafayatb.streamly.data.local.tryEdit
import com.shafayatb.streamly.domain.settings.AppSettings
import com.shafayatb.streamly.domain.settings.DownloadPreferences
import com.shafayatb.streamly.domain.settings.DownloadPreferencesSource
import com.shafayatb.streamly.domain.settings.DownloadQuality
import com.shafayatb.streamly.domain.settings.SettingsRepository
import com.shafayatb.streamly.domain.settings.ThemeMode
import com.shafayatb.streamly.domain.util.DataError
import com.shafayatb.streamly.domain.util.EmptyResult
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch
import kotlinx.coroutines.flow.distinctUntilChanged
import kotlinx.coroutines.flow.map

/** Device-wide settings. Enums are stored by name; a name this version does not know reads as the default. */
internal class DataStoreSettingsRepository(
    private val dataStore: DataStore<Preferences>,
) : SettingsRepository, DownloadPreferencesSource {

    // A store that cannot be read gives the defaults: the app must still start with a theme.
    override val settings: Flow<AppSettings> = dataStore.data
        .map { it.toSettings() }
        .catch { emit(AppSettings()) }
        .distinctUntilChanged()

    override val downloadPreferences: Flow<DownloadPreferences> = settings
        .map { it.downloadPreferences }
        .distinctUntilChanged()

    override suspend fun setThemeMode(mode: ThemeMode): EmptyResult<DataError.Local> =
        dataStore.tryEdit { it[Keys.themeMode] = mode.name }

    override suspend fun setWifiOnlyDownloads(enabled: Boolean): EmptyResult<DataError.Local> =
        dataStore.tryEdit { it[Keys.wifiOnlyDownloads] = enabled }

    override suspend fun setDownloadQuality(quality: DownloadQuality): EmptyResult<DataError.Local> =
        dataStore.tryEdit { it[Keys.downloadQuality] = quality.name }

    private fun Preferences.toSettings(): AppSettings {
        val defaults = AppSettings()
        return AppSettings(
            themeMode = ThemeMode.entries.firstOrNull { it.name == this[Keys.themeMode] } ?: defaults.themeMode,
            wifiOnlyDownloads = this[Keys.wifiOnlyDownloads] ?: defaults.wifiOnlyDownloads,
            downloadQuality = DownloadQuality.entries.firstOrNull { it.name == this[Keys.downloadQuality] }
                ?: defaults.downloadQuality,
        )
    }

    private object Keys {
        val themeMode = stringPreferencesKey("theme_mode")
        val wifiOnlyDownloads = booleanPreferencesKey("wifi_only_downloads")
        val downloadQuality = stringPreferencesKey("download_quality")
    }
}

import kotlinx.coroutines.flow.SharingStarted
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.combine
import kotlinx.coroutines.flow.receiveAsFlow

import streamly.shared.generated.resources.Res
import streamly.shared.generated.resources.settings_save_failed
import streamly.shared.generated.resources.settings_version_value

/** Shows only what the store reports, so a failed save never looks saved. */
class SettingsViewModel(
    private val settingsRepository: SettingsRepository,
    appInfo: AppInfo,
) : ViewModel() {

    private val version = UiText.Resource(Res.string.settings_version_value, listOf(appInfo.versionName, appInfo.versionCode))
    private val dialog = MutableStateFlow<SettingsDialog?>(null)

    val state: StateFlow<SettingsState> = combine(settingsRepository.settings, dialog) { settings, dialog ->
        SettingsState(settings = settings, dialog = dialog, version = version)
    }.stateIn(viewModelScope, SharingStarted.Eagerly, SettingsState(version = version))

    private val _events = Channel<SettingsEvent>()
    val events: Flow<SettingsEvent> = _events.receiveAsFlow()

    fun onIntent(intent: SettingsIntent) {
        when (intent) {
            SettingsIntent.OpenThemeDialog -> open(SettingsDialog.THEME)
            SettingsIntent.OpenQualityDialog -> open(SettingsDialog.DOWNLOAD_QUALITY)
            is SettingsIntent.SelectTheme -> choose { settingsRepository.setThemeMode(intent.mode) }
            is SettingsIntent.SelectQuality -> choose { settingsRepository.setDownloadQuality(intent.quality) }
            is SettingsIntent.SetWifiOnly -> save { settingsRepository.setWifiOnlyDownloads(intent.enabled) }
            SettingsIntent.DismissDialog -> dialog.value = null
            SettingsIntent.NavigateBack -> viewModelScope.launch { _events.send(SettingsEvent.NavigateBack) }
        }
    }

    // A choice dialog needs the current choice to mark, so nothing opens before the read.
    private fun open(which: SettingsDialog) {
        if (state.value.settings != null) dialog.value = which
    }

    private fun choose(write: suspend () -> EmptyResult<DataError.Local>) {
        dialog.value = null
        save(write)
    }

    private fun save(write: suspend () -> EmptyResult<DataError.Local>) {
        viewModelScope.launch {
            write().onFailure { _events.send(SettingsEvent.ShowMessage(UiText.Resource(Res.string.settings_save_failed))) }
        }
    }
}

@Composable
fun SettingsRoot(
    onNavigateBack: () -> Unit,
    viewModel: SettingsViewModel = koinViewModel(),
) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    val snackbarHostState = remember { SnackbarHostState() }
    val scope = rememberCoroutineScope()

    ObserveAsEvents(viewModel.events) { event ->
        when (event) {
            SettingsEvent.NavigateBack -> onNavigateBack()
            is SettingsEvent.ShowMessage -> scope.launch {
                snackbarHostState.currentSnackbarData?.dismiss()
                snackbarHostState.showSnackbar(event.message.resolve())
            }
        }
    }

    SettingsScreen(state = state, onIntent = viewModel::onIntent, snackbarHostState = snackbarHostState)
}

        }

/** The whole row is the switch, so TalkBack reads one control with its title and state. */
@Composable

        verticalAlignment = Alignment.CenterVertically,
        modifier = Modifier
            .fillMaxWidth()
            .heightIn(min = 56.dp)
            .toggleable(value = checked, enabled = enabled, role = Role.Switch, onValueChange = onCheckedChange)

        Column(modifier = Modifier.weight(1f)) {
            Text(title, style = MaterialTheme.typography.bodyLarge, color = MaterialTheme.colorScheme.onSurface)
            Text(detail, style = MaterialTheme.typography.bodyMedium, color = MaterialTheme.colorScheme.onSurfaceVariant)
        }
        Spacer(Modifier.width(16.dp))
        Switch(checked = checked, onCheckedChange = null, enabled = enabled)
    }
}
